<section id="prerequisites">
<div class="section-label">Before You Begin</div>

## Prerequisites

<div class="card-grid-2col">
  <div class="info-card">
    <h3>✅ Required</h3>
    <ul>
      <li><strong>Inference access</strong> for the selected engine; Copilot access/billing for this guide's Copilot example</li>
      <li><strong>GitHub CLI</strong> v2.45.0 or later</li>
      <li>The <code>gh-aw</code> CLI extension</li>
      <li><strong>Admin access</strong> to the target repository</li>
    </ul>
  </div>
  <div class="info-card">
    <h3>🔑 Tokens &amp; Secrets</h3>
    <ul>
      <li>Copilot: <code>copilot-requests: write</code> for supported organization billing, or the <code>COPILOT_GITHUB_TOKEN</code> PAT alternative</li>
      <li><code>GH_AW_AGENT_TOKEN</code> — optional, needed for <code>assign-to-agent</code></li>
      <li>Custom <strong>PAT or GitHub App</strong> — optional, for cross-repo or elevated access</li>
    </ul>
  </div>
</div>
</section>

<section id="install">
<div class="section-label">Setup</div>

## Install &amp; Initialize

<p class="section-desc">Three commands to go from zero to a fully initialized repository. The CLI handles scaffolding, engine selection, and configuration.</p>

<div class="step-grid">
  <div class="step-item">
    <div class="step-num">1</div>
    <div class="step-body">
      <h4>Install the gh-aw CLI extension</h4>
      <p>Adds the <code>gh aw</code> command to your GitHub CLI. Requires GitHub CLI v2.45.0 or later.</p>
    </div>
  </div>
  <div class="step-item">
    <div class="step-num">2</div>
    <div class="step-body">
      <h4>Initialize your repository</h4>
      <p>Run <code>gh aw init --engine copilot</code> in a disposable repository. Current initialization is noninteractive; the engine flag selects Copilot and sets up its integration files.</p>
    </div>
  </div>
  <div class="step-item">
    <div class="step-num">3</div>
    <div class="step-body">
      <h4>Select the inference authentication path</h4>
      <p>Use <code>copilot-requests: write</code> where organization policy and billing support it. Otherwise configure the documented Copilot PAT alternative; do not assume every engine needs that token.</p>
    </div>
  </div>
</div>

<div class="code-block">
  <div class="code-header"><span>Terminal</span></div>
  <pre>{`# 1. Install the gh-aw CLI extension
gh extension install github/gh-aw

# 2. Initialize your repository
gh aw init --engine copilot

# 3. Only for the Copilot PAT alternative:
gh secret set COPILOT_GITHUB_TOKEN -R owner/repo`}</pre>
</div>

<div class="callout">
  <strong>💡 What does <code>gh aw init</code> do?</strong> It configures repository files, the dispatcher skill, and optional engine/MCP integrations. It does not prompt for engine selection or configure inference secrets. Check <code>gh aw init --help</code> for your installed release.
</div>
</section>

<section id="token">
<div class="section-label">Authentication</div>

## Choose authentication — not every workflow needs a PAT

<p class="section-desc">Current Copilot workflows can use <code>permissions: copilot-requests: write</code> with supported organization billing, without a PAT. The steps below apply only to the alternative user-token path. With that permission configured, the PAT is ignored for inference. See the <a href="https://github.github.com/gh-aw/reference/auth/">official authentication reference</a>.</p>

<div class="step-grid">
  <div class="step-item">
    <div class="step-num">1</div>
    <div class="step-body">
      <h4>Generate a fine-grained token</h4>
      <p>Go to <a href="https://github.com/settings/personal-access-tokens/new" target="_blank" rel="noopener noreferrer">github.com/settings/personal-access-tokens/new</a> and select <strong>Fine-grained personal access token</strong>.</p>
    </div>
  </div>
  <div class="step-item">
    <div class="step-num">2</div>
    <div class="step-body">
      <h4>Grant Copilot permission</h4>
      <p>Under <strong>Account permissions</strong>, set <strong>Copilot Requests</strong> to <strong>Read-only</strong>. No other permissions are required for the base token.</p>
    </div>
  </div>
  <div class="step-item">
    <div class="step-num">3</div>
    <div class="step-body">
      <h4>Store as a repository secret</h4>
      <p>Run <code>gh secret set COPILOT_GITHUB_TOKEN -R owner/repo</code> and paste the token when prompted — or add it via the repository Settings → Secrets → Actions page.</p>
    </div>
  </div>
</div>

<section id="first-workflow">
<div class="section-label">Build</div>

## Your First Workflow

<p class="section-desc">Start with the staged, manual-dispatch backlog briefing shown on Home. Compile and review it in a disposable repository. Compilation checks syntax and generated configuration, not the truth of future agent findings.</p>

<div class="step-grid">
  <div class="step-item">
    <div class="step-num">1</div>
    <div class="step-body">
      <h4>Copy the bounded example</h4>
      <p>Copy <code>examples/backlog-briefing.md</code> from this overview into a disposable repository's <code>.github/workflows/</code>. Keep <code>staged: true</code> and the manual trigger for the first demonstration.</p>
    </div>
  </div>
  <div class="step-item">
    <div class="step-num">2</div>
    <div class="step-body">
      <h4>Compile to a hardened Actions workflow</h4>
      <p>The <code>compile</code> command transforms your Markdown source into a <code>.lock.yml</code> file with pinned actions, sandboxed permissions, and safe outputs.</p>
    </div>
  </div>
  <div class="step-item">
    <div class="step-num">3</div>
    <div class="step-body">
      <h4>Push to your repository</h4>
      <p>Commit both the <code>.md</code> source and the <code>.lock.yml</code> compiled file. GitHub Actions picks up the lock file automatically on the next trigger.</p>
    </div>
  </div>
</div>

<div class="code-block">
  <div class="code-header"><span>Terminal</span></div>
  <pre>{`# 1. Copy examples/backlog-briefing.md into .github/workflows/
#    in a disposable repository, then inspect its permissions.

# 2. Compile to a hardened Actions workflow
gh aw compile .github/workflows/backlog-briefing.md

# 3. Review the .md and generated .lock.yml together.
#    Commit through your normal reviewed development process.
#    Cloud dispatch is a separate, deliberate action.`}</pre>
</div>

<div class="callout">
  <strong>Review before running.</strong> The example is compiler-checked with v1.2.2, not cloud-executed. Manual dispatch still consumes inference/Actions resources. Staged outputs preview a proposed write, not a durable approval queue. To demonstrate, review the run output and explain the human decision; do not enable publishing merely to finish the demo.
</div>
</section>
